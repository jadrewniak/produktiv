# Review presentation

Use for plan, code, completion, simplicity, specialist and closeout reports. This reference governs presentation only; each active rubric retains its scope, evidence requirements, severities and verdicts. A specialist or simplicity pass cannot invent a feature-readiness verdict.

The caller reads local communication preferences and passes language, technical_depth and detail with the original rubric and bounded evidence to an isolated reviewer. If the reviewer cannot read this reference, pass its contents too. Preferences affect explanation, never findings or severity. Without preferences use the user's language, product-technical depth and concise detail.

Lead with the actual outcome and practical consequence. Use short meaningful headings for a substantial report; a small result needs no empty sections. Show verdict/status/severity tokens in inline code, for example `REVISE` or `IMPORTANT`, followed by a plain-language title. Explain the problem, user/system consequence and bounded remedy together; retain precise linked locations and supporting evidence. Group related findings without hiding independent problems or changing severity. Detailed non-technical means fuller explanation, not rubric jargon.

Distinguish findings awaiting validation, confirmed defects, rejected findings with reasons, applied fixes with evidence, and remaining limitations when those states exist. A reviewer reports hypotheses and does not claim fixes. The caller owns reconciliation. State missing checks and weaker independence without presenting them as a clean result. Say how each material finding was settled: `reproduced`, with the command and what it showed; `refuted`, with the run that reached the path and worked; or `inspected`, with why no run settled it, including a run that did not reach the path. State review independence in one line per reviewer: `Reviewer: context=<same-context|fresh-subagent|external-process> | family=<same|different|unknown> | models: <executor> → <reviewer>`, or `Reviewer: none` when no review ran. A model the host or tool does not report is `unknown`. Family compares providers: `same-context` is `same`; an external result's `provider` counts even when its model is unknown; otherwise an unknown model leaves it `unknown`. A fresh context removes shared reasoning, not shared blind spots, so disclose `family=same` for a fresh reviewer too. No findings means none supported in the reviewed scope, not a security certificate or global PASS.

Rubric output fields and examples describe required information in the working payload, not a mandatory user-facing field dump. Render readable Markdown even in subagent replies; do not expose XML/tool wrappers, raw serialization, or a code fence around the whole report. Preserve required rubric fields in a compact technical detail only when useful or explicitly requested. Translate explanatory prose and no-findings messages; retain exact machine-consumed labels only where an actual interface requires them. Use inline code for identifiers/commands and emphasis sparingly for consequences, not every sentence.

An authorized repair report explains what changed and what evidence closes each material finding. Offer only unresolved decisions/actions; do not manufacture a next stage or additional review from presentation rules.
