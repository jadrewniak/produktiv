# Accepted visual handoff

Read this with `references/artifact-resolution.md` when a boundary references accepted design, `.workflow/context/design.md`, HTML or design assets, and when accepting or handing off design.

## Accepted design in the project

Setup maps existing accepted design. An authorized `/pk-design` acceptance/application updates `context/design.md` as a compact index of principles, accepted artifact/scope, stable view/fragment anchors, components/states, fonts/assets and exclusions. Accepted HTML and required assets live under the project's durable documentation/design convention, never only in cache. Read only the referenced views/states/assets relevant to the boundary.

## Acceptance and handoff

An acceptance identifies the chosen artifact/revision and accepted scope, with the owner decision source in the existing design index or artifact. Use the project's existing revision convention or a preserved accepted copy; no mandatory hash schema or new ledger. Partial acceptance names excluded views/states and unresolved proposals. Keep later exploration separate from the accepted copy: a still-existing path or an `accepted` label does not establish that materially edited contents were approved. Reuse evidenced authorization without asking for it again.

Before handing off or consuming a visual dependency, resolve Markdown links relative to their containing document (label project-root paths explicitly). Check the selected fragment exists uniquely and follow its required CSS, scripts, images and font dependencies from the durable location. Include how to reach a dynamic state when its anchor alone does not display it. A selected view may depend on shared styles or state logic outside the fragment; retrieve those dependencies, not the whole gallery. Record external loading assumptions and available fallback instead of claiming offline portability without proof.

Reconcile the Plan's selected references with the current accepted index and relevant artifact contents. If a file, anchor or required asset is missing, recover only from an unambiguous accepted source; do not substitute the newest draft or redesign from prose. A recovered locator does not authorize a read-only consumer to rewrite it. Conflicting acceptance, a material unaccepted edit, or an unrecoverable required reference blocks the affected UI boundary until the design owner resolves it; independent ready work can continue. A materially changed accepted baseline also requires the affected Plan references/route to be reconciled before dependent execution.
