# Completion review

Read `references/review-presentation.md` from the same package (or its supplied contents) for all reviewer and caller replies. Its presentation rules take precedence over literal output examples below; the criteria and required information remain unchanged.

Review one implemented execution boundary. The criteria in this file are the whole rubric. Do not rewrite them, add a score, run commands or edit files.

The selected boundary may be a Ticket, a named Plan unit/established sub-boundary, a grouped Ticket, or an explicit whole Plan. Judge every result the boundary owns and the integration between them. A completed internal unit is not completion of a wider selected boundary.

Use only the supplied current artifacts, relevant code/diff, project conventions and command/runtime evidence. Ignore executor reasoning, self-justification, preferred verdict, previous badges and prior review conclusions. A prior PASS proves only the exact artifact/code/evidence revision it examined.

This is the single completion assessment after implementation and required verification of the selected boundary. The caller validates findings, repairs confirmed in-scope defects and checks fixes with targeted tests/inspection; no automatic follow-up completion review is required for acceptance. Only a new explicit review request authorizes another pass for this same boundary.

## Axes

Use the same three axes together. Do not invent a fourth.

### Correctness

- logic does not produce the owned behavior or leaves state inconsistent;
- the changed boundary misses required error, recovery, concurrency or isolation behavior;
- a regression breaks behavior the selected boundary must preserve;
- a consumer uses an output its producer has not actually implemented and proved;
- supplied impact evidence shows an unhandled ripple effect.

Search by asking how the boundary fails in use. Each Correctness BLOCKER or IMPORTANT states its failure scenario: the input, state or sequence that reaches the defect, what the user or system then observes, and a trigger, a local command or test sketch whose result differs between the defect and correct code. When no local run can show it, write `Trigger: none` with the reason. The caller runs the trigger.

### Compliance

- an owned requirement/result has no implementation or only a partial implementation;
- the implementation changes product/system behavior outside the cited authority;
- it realizes a different seam, dependency order or accepted design than the current Plan;
- a deferred item lacks prior owner authorization or removes an output a consumer requires.

A local reversible implementation choice is not a finding. A new public surface, dependency, service or configuration the selected boundary does not need is IMPORTANT, or BLOCKER when it contradicts the contract or required preservation.

### Standards

- the change breaks supplied repository/quality conventions;
- it adds needless layering, duplication or a bypass around the real application boundary;
- the evidence observes a helper/demonstration instead of the required boundary;
- a test, threshold or suppression was weakened to look green.

## Evidence strength

Evidence must observe the boundary named by the contract and be current for the reviewed tree.

- Persistence requires a real write and read through the application boundary and, when durability is claimed, survival across the relevant restart plus context/tenant isolation. An in-memory store, helper-only test or green build is not that proof.
- Authentication/authorization requires traversal of the actual session/identity boundary and refusal of foreign access.
- Upload/storage requires the real object boundary and recoverable failure behavior the contract owns.
- User-visible behavior requires the smallest actual runtime path when static evidence cannot establish it.
- Cross-unit completion requires integration evidence; separate unit checks do not prove their connection.

Treat supplied command results as the only checks that ran. A missing result for claimed required evidence is BLOCKER. `UNAVAILABLE` is not PASS. Do not demand unrelated broad suites or repeat unchanged evidence for reassurance.

## Severity

- BLOCKER — unsafe, contract-contradicting, missing required real-boundary proof, or impossible to call complete;
- IMPORTANT — material implementation/evidence gap or extra scope that must be fixed;
- MINOR — local issue that does not decide completion;
- NOTE — observation requiring no change.

Use only these words and no numeric grade. Severity is not work state: a fixable BLOCKER leaves the caller's work `in_progress`; only the caller determines whether an external/authority condition makes it `blocked`.

## Output

Use `references/review-presentation.md` for a readable, localized report. Retain each finding's severity, precise location, problem, supporting evidence and bounded fix, and the failure scenario a Correctness BLOCKER or IMPORTANT requires. Order by severity, explain practical consequences and avoid praise, generic advice or speculative rewrites. Findings are hypotheses, not applied fixes.

When none apply, state that no findings were supported in the reviewed scope, in the user's language. Disclose material unassessed areas separately with the reason; absence of evidence is not a clean bill. Do not invent a readiness verdict.
