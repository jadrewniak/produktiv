# Plan review

Read `references/review-presentation.md` from the same package (or its supplied contents) for all reviewer and caller replies. Its presentation rules take precedence over literal output examples below; the criteria and required information remain unchanged.

Review one Plan before code: can a cold executor realize the approved product/system/design contract through a coherent, proportionate route without inventing a material decision? Read-only. Do not edit artifacts, write a replacement Plan, grant owner consent or add a score.

## Inputs and authority

Use only the supplied current Plan, canonical product source (Issue, otherwise Source brief), canonical Spec on the Issue path when present, accepted design fragments relevant to UI, project/quality/ADR excerpts, current repository files and actual optional evidence. Ignore author reasoning, preferred verdict, prior review approvals and status badges as proof; retain actual owner-choice/delegation evidence. Missing input is missing evidence.

Issue owns product/UX/domain. Spec owns binding durable/shared/compatibility/costly system contracts. Accepted design owns presentation. Plan owns route. Repository shows current reality. Review verifies these responsibilities; it cannot choose a costly foundation for the owner. A prior substantiated durable choice or delegation is sufficient and must not be routinely reopened. An accepted ADR badge, an author's claim of delegation, or assigning a decision to Plan does not establish owner consent. Compare relevant open/deferred project decisions with the supplied choice source; missing provenance for a new material choice is a gap.

## Default axes

Judge all six; report one defect under its owning axis.

1. **Authority.** Trace every material target/change/proof to binding authority. Reject promoted notes, inferences, repo facts and tighter tests. Confirm owner choice/delegation for a new interdependent auth/persistence/storage foundation; absence is an upstream decision gap, not reviewer approval.
2. **Coverage and cold-executor readiness.** Every material acceptance/contract/design outcome has an owner, route and sufficient proof. Allocate state, IO, domain, UI, migration and configuration responsibilities to material existing or intentionally new files/modules. Ask what structure, integration, behavior or proof a cold executor would still need to design. Labels and directory lists are not readiness.
3. **Architecture.** Check actual ownership, dependency direction, reuse and blast radius against current files/ADRs. New modules earn boundaries by responsibility/coupling, not file-count quotas. Do not propose a replacement architecture.
4. **Simplicity.** For each new layer/dependency/service/config/storage boundary, identify the current requirement, failure without it, existing seam alternatives and maintenance/migration/removal burden. A pure simplification preserving authority is Consider; safety/data/required behavior cannot be simplified away.
5. **Consistency and execution frontier.** Compare consumed/produced shapes, lifecycle, errors, persistence writes/reads/migrations, UI/operation ownership and dependency order. A consumer starts only after its producer result and proof exist, except a separately named independently verifiable sub-boundary with existing proof. Unit numbering or “independent” is not readiness. Stable IDs and exact accepted design refs survive repairs.
6. **Verification and environment.** Require cheapest evidence at the actual risk boundary. Confirm existing commands from quality/manifest/task runner/build/CI; a lockfile alone does not define one. A planned new check names producer, defining file/invocation, prerequisites and observable. Persistence needs real write/restart/read/isolation, auth needs real session/denial, storage needs object/recovery, and cross-unit behavior needs integration. Build/helper/in-memory demo is insufficient. New environments name runtime/dependency command producers, service startup, non-secret fixture config, fixture-only reset and evidence capture. Unavailable infrastructure stays a gap, not a demo substitution.

Verification remains contract-exact. Preserve all required non-interference directions and every required inverse/retry/recovery path. Forward success cannot stand in for recovery.

## Conditional tracks

Judge a matching track in text; the owning skill selects optional tools through policy. Missing tools do not erase findings.

- dependency/source/security/privacy/migration/performance tracks follow their named risk;
- architecture delta applies to a new/reversed ownership, persistence or integration boundary;
- adversarial applies to poorly evidenced or hard-to-reverse security, concurrency/idempotency, persistence, API removal, irreversible migration or wide blast radius.

A new complex auth/persistence/storage foundation always needs this route review before code, but still needs separate owner choice/delegation. A small local change in an existing contract does not inherit this ceremony.

## Findings, owners and verdict

- **Blocker:** destination contradicts product/binding contract, accepted design or safety/data protection.
- **Required:** material authority, contract, route, wiring, environment, consistency or evidence gap.
- **Consider:** concrete simplification preserving all authority; never a missing contract/proof.

Every Blocker/Required has one owner: `/pk-discover` for unresolved product/UX/domain meaning; `/pk-to-spec` for an unclosed/defective system contract (it can first persist agreed product scope when no Issue exists); `/pk-to-plan` for route, allocation, wiring, environment, dependency, stale ref or verification repairs already settled by authority. Never `/pk-implement`. Consider has no mandatory owner. These are responsibilities, not mandatory command round-trips: an authorized author may resolve a bounded owner decision and update its source through `policies/decisions.md`. The reviewer remains read-only and cannot supply consent.

Verdict is `REVISE` when any Blocker/Required exists. Otherwise `ACCEPT`, or `ACCEPT WITH KNOWN TRADEOFFS` only for authority-supported explicit tradeoffs with owner and ceiling/revisit trigger. REVISE needs another review after repair.

## Reviewer payload

Lead with exactly `Verdict: ...`, then material impact and one grouped repair proposal or `No material findings.` Retain `Product source: ...` and `Spec: ...`. Each finding includes severity, precise location, axis, decision kind, mandatory owner, source evidence, impact and bounded remediation. No praise, retelling, score or speculative rewrite.

For a judged architecture delta without a rendered diagram, disclose that structure was reviewed in text and why no diagram was rendered. This disclosure is not a finding.

This is the working payload, not a mandatory user-facing field dump. The caller presents the verdict, consequences, decisions and grouped repair in the user's language and configured depth/detail, retaining severity and recoverable evidence/locations. Never expose tool wrappers as prose.
