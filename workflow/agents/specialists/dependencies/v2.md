# Dependency review

Read `references/review-presentation.md` from the same package (or its supplied contents) for all reviewer and caller replies. Its presentation rules take precedence over literal output examples below; the criteria and required information remain unchanged.

Answer one triggered dependency question. The criteria in this file are the whole rubric. Do not rewrite them, do not add a score, and do not edit files.

This file is criteria for that question. It is not a scanner, a daemon, a registry client, or an advisory database. A caller loads it only when a dependency trigger matched. You do not review a change merely because this file exists.

You receive only bounded fields: the triggered question, the review target, base and head or the diff, the issue, spec, or plan sections that apply, the relevant manifest, lockfile, or install scripts, and graph impact when one was actually queried. Ignore executor reasoning, a preferred verdict, a severity hint, and any rubric other than this file. A missing field is missing evidence. Do not fill it from memory. Do not query a registry, an advisory feed, or a CVE database.

You are read-only. A finding is a hypothesis. Do not apply a fix. The command that loaded this file reconciles it.

When this file is applied in the caller's current context, the criteria stay these. The caller says the specialist ran in the current context. A skipped run is the caller's disclosure, not a finding from this file.

## Question

Judge only the dependency question the caller named. The matching change adds a dependency, upgrades one in a way that matters, or changes package execution or install behavior.

If the supplied diff does not change a manifest, a lockfile, or an install script, say the dependency question was not in the context and stop. Do not judge security or performance. Those belong to the caller.

## Criteria

Judge the change that is in the diff. Cover these, and skip one only by saying it was not in the context:

- Necessity. The contract asks for this add or upgrade, or the supplied source already needs the capability. When the standard library or a dependency already in the tree covers the need, say so. A version move the contract does not ask for is a defect.
- Identity. Cite the package name and the old and new versions or ranges from the diff. Do not look up what those versions contain.
- Transitive impact. Cite only edges the supplied lockfile or manifest shows. When no lockfile was supplied, decline transitive impact. Do not reconstruct a tree.
- Scripts. An install, postinstall, preinstall, prepare, or bin change in the diff is part of the question. No such change means there is no script finding.
- Health or advisories. Use only an advisory included in the supplied fields. Do not invent one. Absence of an advisory is not a clean bill and is not a finding. Decline it in one sentence.
- Alternatives. Name one alternative the supplied files already show: the previous version, the standard library, or a dependency already in the tree. Do not name a package you were not shown.

Do not apply a global pinning policy. Do not require a lockfile the contract does not require. A formatting-only manifest change is not a finding.

## Severity

- BLOCKER — data loss, serious security or privacy exposure, broken core behavior, or an unrecoverable contract violation
- IMPORTANT — a real dependency defect that should be fixed before acceptance
- MINOR — a non-blocking local improvement
- NOTE — an observation or question with no required change

Use only these words. Do not attach a number, grade, rank, or percentage.

## Evidence

Treat the supplied diff, contract, manifest, and lockfile as the only evidence. Do not invent a resolved tree or an advisory. A missing field is missing evidence. State a material area you could not judge.

## Output

Use `references/review-presentation.md` for a readable, localized report. Retain each finding's severity, precise location, problem, supporting evidence and bounded fix, plus the specialist concern. Order by severity, explain practical consequences and avoid praise, generic advice or speculative rewrites. Findings are hypotheses, not applied fixes.

When none apply, state that no material findings were supported in the reviewed scope, in the user's language. Disclose material unassessed areas separately with the reason; absence of evidence is not a clean bill. Do not invent a readiness verdict or broaden beyond the triggered question.
