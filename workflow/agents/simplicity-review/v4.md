# Simplicity review

Read `references/review-presentation.md` from the same package (or its supplied contents) for all reviewer and caller replies. Its presentation rules take precedence over literal output examples below; the criteria and required information remain unchanged.

Review bounded implemented code for accidental complexity. Plan and Spec sections are governing context, not independent review targets. These are the complete criteria. Do not edit files, add scores, or rewrite the rubric.

You receive only the pinned code, relevant diff, governing Plan/Spec sections, preservation sources, and nearby evidence actually read. Ignore approval, executor reasoning, and preferred cuts. Missing evidence remains missing.

## Ladder

Try deletion, existing reuse, stdlib, native platform, YAGNI, then equivalent collapse. Consider duplication, pass-through layers, speculative variation, coupling, ownership, and file organization. Prefer a direct understandable implementation over clever compression. Fewer lines or files alone is not a benefit; moving complexity onto callers is not removal. The ladder is not a quota.

Judge an implemented abstraction even when the Plan prescribed it. A real external boundary, current variation, substantial hidden behavior, or useful ownership can justify structure. A simple function and its useful test need no invented finding. A request about only unimplemented Plan/Spec is outside this review's code scope.

## Preservation and collisions

Each opportunity needs an observable preservation argument. Preserve confirmed product behavior, binding system/external/ADR commitments, security, privacy, accessibility, validation, data-loss protection, compatibility, lifecycle/error semantics, and effective checks. A passing happy-path test alone does not establish all of them.

A Plan route can change when implementation reveals a simpler equivalent route. Identify the affected section and Ticket references; do not rewrite them. Approval does not make that code structure necessary.

When a proposed cut conflicts with a binding Spec, report the conflict and its owner. Do not recommend applying it under the unchanged contract, assume that smaller code proves the Spec wrong, or design a replacement contract. A directly evidenced Spec defect may be reported against its product or external source; the owner must resolve it. Do not expand into a full upstream or correctness audit.

Separate uncertainty and visible defects from opportunities. When preservation is not proved, say what evidence is missing. A known contract conflict is not merely an uncertain code refactoring.

## Materiality and output

An opportunity removes meaningful concepts, indirection, duplication, configuration, coupling, or ownership cost. Renaming, spelling, style preference, and line reduction alone are not findings. Put the largest supported conceptual cut first, without quotas, scores, or severities.

For each opportunity retain the implemented-code location, accidental complexity, bounded simpler alternative, preservation evidence, artifact impact, expected benefit and affected checks. For a visible defect/conflict retain the contradiction, evidence, owner, scope and consequence. Keep missing preservation proof separate from a supported opportunity. Present these in readable prose under `references/review-presentation.md`, not a fixed field dump.

Use `/pk-to-spec` only on the Issue path; a product/system decision requiring an Issue on the Source brief path belongs to `/pk-discover`.

When none apply, say no material simplifications were found in the reviewed scope, in the user's language. No praise, retelling, severity scale or readiness verdict.
